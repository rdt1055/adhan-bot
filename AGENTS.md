# Adhan Bot: agent rules (always on)

A Discord bot for small Arabic-speaking communities in Algeria. One Node.js process, one bot account.
Full project state, design decisions and history are in `@docs/PROJECT.md`. Read it at the start of a task and update its **Status** section at the end of the session.

## Hard rules (never break these)
1. **Never read, print, open, copy or commit `.env`.** It holds the live bot token. Never put a token in logs, code or reports.
2. **Never run `node bot.js` or anything that logs in to Discord.** The bot is live in real servers; only the owner starts it. You may run `node --check <file>`, offline unit tests, and the scripts in `scripts/` (they only read/write local files and public data sources).
3. **All user-facing text is Arabic. Do not change Arabic strings, command names, prayer audio mappings or the `serverconfig.json` format** unless asked. New user-facing text must be Arabic too.
4. **Time is always `Africa/Algiers` (UTC+1, no DST)** through the helpers in `lib/algiers-time.js`. Never use host-local `Date` methods for scheduling or display.
5. **Religious content is never generated by AI**: no hadith, ayah, tafsir, sharh or grading text written by a model. Only data from a named source, shown with its source.
6. **Fail-safe for religious data:** if a match, grade, number or text cannot be proven, drop the item and say so. Never guess, never "fix" by approximation. A dropped item costs little; a wrong one costs a lot.
7. **Source text is never altered** except: whitespace collapse/trim, Markdown escaping for display, and splitting at clause punctuation or spaces. Any other repair must be an explicit, counted, owner-approved rule.
8. No new dependencies without asking first (current: discord.js 14, discord-voip 7, libsodium-wrappers, ffmpeg-static, axios, dotenv; Node 22). Node's built-in `fetch` is fine.

## Code conventions
- Node.js **CommonJS**. A feature is one file exporting `{ name, slashCommands, prepare?, onReady?, onInteraction?, onMessage? }`, added with one line in the `features` array in `bot.js`. `onInteraction`/`onMessage` return `true` when they handled the event, otherwise `false`.
- Slash commands are registered in one bulk PUT: one invalid command blocks every update. Build new commands with `SlashCommandBuilder` and validate them (e.g. `.toJSON()`) before finishing.
- Persistent runtime state uses `lib/state-store.js` (atomic JSON in `data/`). Server settings use `lib/config-store.js`; its `setServerConfig` is a **shallow merge** (passing `{ ahadith: {...} }` replaces the whole `ahadith` object).
- Scheduling for new features uses the tick-based `lib/daily-scheduler.js` (not long `setTimeout`).
- Voice playback (adhan): `NoSubscriberBehavior.Pause`, wait for Ready, one idempotent `cleanup()`, the playback promise must always settle, destroy a connection only if its state is not already `destroyed`.
- Discord limits: embed description 4096, 6000 total per message; ephemeral replies for per-user content; custom IDs `feature:action:arg`.
- Optional features must stay **dormant** in servers that did not enable them, and must degrade silently when their data files are missing.

## Do not touch (on hold by the owner)
The **sharh** feature (`lib/sharh-store.js`, `scripts/build-sharh.js`, `scripts/probe-*.js`, the sharh button code in `ahadith.js`) is dormant. Do not modify, extend or delete it; do not propose reviving it.

## Context hygiene (saves quota)
- Never open or print whole data files: `data/hadith-pool.jsonl` (15 MB), `data/hadith-index.json`, `data/quran.json`, `data/tafsir-muyassar.json`. Use `head`, `jq`, `grep` or a small script.
- Ignore `.git/`, `node_modules/`, `*.mp3`, `build-report.txt`.

## How to work with the owner
- He is not a professional developer and uses Windows `cmd` (not PowerShell). Give commands for `cmd`, quote paths.
- Discuss trade-offs and state your default as a decision **before** building anything non-trivial. For multi-file or new-feature work, produce a plan first and wait for approval.
- Make small, reviewable changes. Suggest a git commit **before** a task and after it passes. Deliver complete files, not fragments.
- Say plainly what you could not verify (anything needing real Discord, real audio playback, or his judgment of Arabic). Never claim "tested" for something you did not run. Give him a short checklist of what to test in Discord.
- Prefer honesty over speed. If you are unsure, say so.
